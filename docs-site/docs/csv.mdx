## CSV with clinical data as input

:::note[Note]
This conversion method helps users who don't have the tools or expertise to transform their raw clinical data. It aims to convert **essential fields needed for comparing data across studies**.

If you use our tool and identify areas for improvement, please contact us or create a GitHub issue. Thank you.

:::

<Tabs>
<TabItem value="command-line" label="Command-line">


When using the `convert-pheno` command-line interface, see [Common CLI Patterns](usage) for reusable command forms.

:::warning[CSV Separator Notice]

Please note that the default separator for CSV files is `;`. If your file uses a different character (e.g., `,` or `:`), please specify it using the `--sep` option.

:::
```
    convert-pheno -icsv clinical_data.csv --mapping-file clinical_data_mapping.yaml -obff individuals.json --sep ,
    ```

### Write OMOP-CDM tables

The same mapping file can drive a focused CSV-to-OMOP ETL route. Convert-Pheno first maps each source record to its internal `BFF` representation and then applies the supported [BFF-to-OMOP mapping](bff2omop). The intermediate `BFF` file is not written or supplied by the user.

```bash
convert-pheno -icsv clinical_data.csv \
  --mapping-file clinical_data_mapping.yaml \
  --sep , \
  -oomop --out-dir omop_out/ \
  --ohdsi-db
```

OMOP output requires the Athena-OHDSI database selected by `--ohdsi-db`; see [OMOP-CDM](omop-cdm) for its installation and location options.

:::info[How this differs from a traditional OMOP ETL workflow]
This supported route does not require installing White Rabbit, Rabbit-in-a-Hat, or Usagi. Instead, the `Convert-Pheno` mapping file describes how source fields become `BFF` clinical concepts, and the built-in `BFF`-to-OMOP mapping writes the supported OMOP tables.

This is an alternative workflow, not a one-for-one implementation of those tools. Convert-Pheno does not automatically profile an unfamiliar CSV or make terminology-curation decisions. Review the source data, mapping file, optional search audit, and generated OMOP tables before loading them into a database.
:::

The route is not an unrestricted column-to-table loader. Source content must be expressible through the supported `beacon.individuals` [mapping-file fields](tbl/mapping-file), and OMOP output is limited to the tables and fields documented under [BFF to OMOP](bff2omop).

By default, the generated `BFF` keeps a copy of the source row under
`info.CSV_columns` so users can audit mapped values against the original
input. Use `--no-source-info` to omit that raw source snapshot.

Please refer to the [Convert-Pheno tutorial](https://cnag-biomedical-informatics.github.io/convert-pheno/tutorial/#how-to-convert) for more information.

:::info[How do I emit more than `individuals`?]
Mapping-file conversions can also emit synthesized Beacon `datasets` and `cohorts`. Keep `-obff` to select `BFF` output, then add `--entities` and `--out-dir`:

```bash
        convert-pheno -icsv clinical_data.csv --mapping-file clinical_data_mapping.yaml -obff --entities individuals datasets cohorts --out-dir out/
        ```

The top-level `beacon` section of the mapping file can override metadata for these synthesized entities. Raw CSV input does not currently generate first-class Beacon `biosamples`.

:::

<TabItem value="api" label="API">


While it is *technically possible* to perform a transformation via the `Convert-Pheno` API, we don't think this is how most people will transform CSV files (due to the need of the mapping file). Therefore, we recommend using the **command-line** version.

If you still want to call the API, the request payload uses explicit `conversion`, `input`, and `options` sections:

```json
    {
      "conversion": "csv2bff",
      "input": {
        "in_file": "clinical_data.csv",
        "mapping_file": "clinical_data_mapping.yaml"
      },
      "options": {
        "sep": ","
      }
    }
    ```

For interface-wide guidance, see [Ways to Run Convert-Pheno](choose-an-interface) and [HTTP(s) API](use-as-an-api).
